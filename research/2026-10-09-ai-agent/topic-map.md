# 彻底精通【AI Agent】的 40 个核心问题
> 层次：初级实操者（有限经验）　目的：应用实践　生成日期：2026-10-09
> 标签：🔴 核心　🌐 需核实时效　⭐ 推荐选题（适合写成文章）

## 第一部分：基础层（是什么？——解构与定义）
1. 🔴 Agent 和"一次性调用大模型"的本质区别是什么？用"模型在循环中自主调用工具、直到完成任务"这个定义，能解释哪些 Agent 特有的现象（成本难预估、结果不稳定、会自己纠错）？
2. 🔴 工具调用在技术上是怎么实现的：模型如何得知有哪些工具、如何决定调用哪一个、调用结果又如何回到上下文？
3. "思考-行动-观察"循环（ReAct）分别弥补了"只推理不行动"和"只行动不推理"的什么缺陷？它的代价是什么？
4. 🔴 上下文窗口对 Agent 意味着什么？为什么往上下文里塞更多信息，常常反而让 Agent 表现变差？上下文工程要解决的核心问题是什么？
5. Agent 的"记忆"本质上有哪几种（上下文内、外部检索、文件或状态持久化）？各自适合存什么、不适合存什么？
6. 工作流（预先编排好的固定路径）和自主 Agent（由模型决定路径）的边界如何定义？两者之间有哪些中间形态？
7. 为什么单步正确率看起来很高的 Agent，在多步任务上的端到端成功率可能大幅下降？误差是如何逐步累积的？
8. Agent 中的"规划"具体指什么？先写完整计划再执行，和边做边调整，分别在什么情况下更好？
9. 反思和自我纠错为什么有时有效、有时越改越错？它依赖什么前提（例如可验证的外部反馈）？
10. Agent 的能力上限由哪些因素共同决定（模型推理能力、工具质量、上下文管理、环境反馈）？如何判断当前的瓶颈在哪一环？

## 第二部分：连接层（有什么？——结构与分类）
11. 🔴 常见的 Agent 设计模式有哪些（提示链、路由、并行、编排者-执行者、评估者-优化者、自主循环）？各自适合什么样的任务？
12. ⭐ 单 Agent 和多 Agent 系统怎么取舍？多 Agent 在什么情况下真正带来收益，什么情况下只是增加成本和故障点？
13. 多 Agent 协作有哪些拓扑结构（主管-下属、流水线、对等协作）？它们在信息传递和错误传播上有什么差异？
14. 🔴🌐 MCP（模型上下文协议）解决什么问题？它与直接写函数调用、与 Agent 之间的通信协议（如 A2A）如何分工？
15. 🌐 Agent 的技术栈分哪几层（模型、框架或 SDK、工具协议、执行环境、观测与评估）？每一层的选型标准是什么？
16. 🌐 用现成框架，还是直接调用模型 API 自己写循环？判断标准是什么？什么时候框架会变成负担？
17. 🌐 为 Agent 选择"大脑"模型时，应该看哪些维度（工具调用可靠性、长上下文表现、推理深度、速度、成本）？如何用自己的任务实测，而不是只看排行榜？
18. 通过 API 操作的 Agent 和通过界面操作（浏览器、电脑使用）的 Agent 各有什么优劣？什么情况下只能用后者？
19. 代码 Agent、研究 Agent、客服 Agent、数据分析 Agent 这几类垂直 Agent，在架构上有什么共性和差异？
20. 🌐 Agent Skills 这类"按需加载的能力包"，和提示词、工具、子 Agent 有什么区别？渐进式加载解决了什么问题？

## 第三部分：应用层（如何做？——方法与实践）
21. ⭐🔴 拿到一个业务任务时，如何判断它该用固定工作流、带部分自主性的工作流，还是完全自主的 Agent？有哪些可操作的判断标准？
22. 🔴 如何为 Agent 设计好用的工具：名称、描述、参数、返回格式、错误信息分别怎么写，才能让模型少犯错？
23. 如何写 Agent 的系统提示词，清楚界定角色、目标、权限边界、停止条件和输出格式？
24. ⭐🔴 如何为 Agent 建立评估集：选哪些任务、如何判定成功、如何同时衡量成功率、成本和耗时，并用它判断每次改动是变好还是变坏？
25. Agent 陷入死循环（比如反复调用同一个失败的工具）时，如何用步数上限、重复检测、预算熔断等机制来防护？
26. 工具调用失败时，如何设计重试、参数修正、降级、向人求助这几层处理策略？
27. 长任务中上下文快满时，如何裁剪、摘要、转存到外部，同时不丢失关键信息？
28. 如何阅读 Agent 的执行轨迹（trace）来定位问题：怎样区分是提示词、工具描述、上下文还是模型能力造成的？
29. 哪些操作应该插入人工确认？如何设计暂停、审批、恢复的流程，又不让人工环节变成瓶颈？
30. 如何把企业已有的 API 或数据库，低成本且安全地封装成 Agent 可调用的工具（包括权限和读写划分）？

## 第四部分：前沿层（怎么用？——实战与内化）
31. ⭐ 复盘公开的 Agent 失败案例，最常见的根因是什么？其中有多少是模型本身的问题，有多少是数据、上下文、权限和流程的问题？
32. ⭐ 一次 Agent 任务的成本由哪些部分构成？如何通过模型分级、缓存、减少轮次、控制子 Agent 数量来优化？
33. 🔴 提示词注入（尤其是通过网页、文件、工具返回内容进行的间接注入）是怎么发生的？架构层面有哪些真正有效的防御手段？
34. 🌐 Agent 的执行环境如何做隔离：沙箱、最小权限、网络限制、密钥管理分别能防住什么风险？
35. 🌐 公开的 Agent 基准测试（编程类、网页类、电脑操作类）到底在衡量什么？为什么基准分数和真实业务表现之间常有明显差距？
36. 如何把 Agent 的失败轨迹转化为改进：哪些环节可以自动化（更新提示词、补充评估用例），哪些必须由人来判断？
37. 团队引入 Agent 之后，人的工作如何重新分工：谁定义任务、谁审核结果、谁对结果负责？
38. 🌐 在隐私敏感的场景下，用本地小模型构建 Agent 的可行边界在哪里？哪些任务能做，哪些不能？
39. 设计一个综合实战项目：从选定一项真实的重复性工作开始，到上线一个有评估、有监控、有人工兜底的 Agent，关键里程碑和验收标准分别是什么？
40. 如何从做过的 Agent 项目中，沉淀出一套"什么时候用、怎么设计、怎么验收"的个人准则？

## ⭐ 推荐选题（适合写成文章）
- **第 12 题**（单 Agent 还是多 Agent）：多 Agent 很热，但很多场景并不需要。适合正在做选型的开发者和技术负责人。
- **第 21 题**（工作流还是 Agent）：初学者最常见的误区就是什么都想上 Agent。实用价值高，适合业务负责人和开发者。
- **第 24 题**（建立评估集）：大多数人跳过的一步，却是 Agent 能否上线的分水岭。干货属性强，适合实操者。
- **第 31 题**（失败案例复盘）：案例天然有故事性，便于传播。适合广泛的技术读者。
- **第 32 题**（成本优化）：成本失控是上线后的真实痛点，有具体方法可讲。适合已经在跑 Agent 的团队。

## 时效校准（检索于 2026-10-09）
- "上下文工程"已被普遍视为比"提示词工程"更核心的能力：重点从怎么写提示词，转向管理 Agent 能看到的全部信息。（来源以从业者和厂商文章为主）
- Agent Skills（按需加载的能力包、渐进式加载）在 2025 年底出现，并被多家厂商的工具采用；具体的采纳时间线未经独立核实。
- MCP 与 A2A 已转由 Linux 基金会下的 Agentic AI Foundation 托管；主流观点认为两者是互补关系（MCP 管工具接入，A2A 管 Agent 间通信），MCP 的实际采用范围明显更广。（采用数据多来自二手博客）
- 生产环境中的可靠性问题被反复提及：多步任务的误差累积、基准分数与真实表现之间的差距、未经校准的"模型评委"。多篇文章认为，大量失败源于数据、上下文和治理，而不是模型本身。（相关统计数字多数无法追溯到一手来源，第 6 步需要核实）
- 长任务能力（检查点、失败恢复）和可观测性（完整轨迹记录、成本上限）被视为当前的工程重点。
